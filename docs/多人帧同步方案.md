# 多人比赛：帧同步方案

> 2026-11-09 草案，**还没开始做**。第 1 节是要先拍板的几件事，每件都附了推荐。
> 参考了三个兄弟项目：funny（Nivara，已上线的 PvP）、daydayup（Blightbloom，联机合作，`design/06-netcode-determinism.md`）、standing（`docs/coop.md` 是同类方案，`engine/README.md` 是确定性规则）。

## 0. 结论

- **可行，而且起点比 standing 还好。** moto 的模拟层从第一天就照帧同步的路子写：
  - 30 Hz 固定步长，`src/sim` 不碰 DOM 和 Three.js；
  - 随机数全部来自带种子的 `Prng`（每种用途一条流）；
  - 只用加减乘除和 `Math.abs/min/max/round`。
- **实测：**
  - 同一个种子跑两遍，终局状态逐字节相同；
  - 桌面上一帧 17.5 µs（10 局 50,884 帧用了 0.9 s），一整局 4,500 帧重算不到 0.1 s。
- **做法：直接移植 daydayup 那套。** 服务器只转发输入、按节拍出帧，自己不跑模拟；客户端预测只放在渲染层。
- **赛车跟 daydayup 的射击游戏有一处不同：只预测自己的横向位置（x），不预测前进方向（z）。** 第 4 节解释原因。
- **规模：** 联网部分约 17–25 个工作日。第 2 节"确定性护栏"花 1–2 天，建议现在就做，单机开发照常进行。

## 1. 先拍板的事

### 1.1 玩法形态

| 选项 | 说明 |
|---|---|
| **A. 好友房：2–4 个真人，AI 补满 8 人** ✅ 推荐 | 房间码加分享链接，不做匹配，跟 standing 的 coop 一样。现有 7 个 AI 对手正好用来补位 |
| B. 公开匹配 | 要有足够的同时在线人数，而 Playgama 的流量现在还说不准；要做匹配服务（funny 的 matchsvc） |
| C. 本地分屏 | 不用联网，但手机上没法分屏，跟目标平台不合 |

### 1.2 升级要不要带进多人局

- 现在升级是存档里的（极速、操控、耐打各 0–6 级）。好友之间进度不同，带进去的话老玩家会碾压新玩家。
- **推荐：多人局统一按 3 级算（"同车竞速"）。** 奖金照常进各自的存档。
- 以后真要做排行或公开匹配，再考虑按升级分房。

### 1.3 领跑威胁、警察、宿怨，人多了怎么算

| 系统 | 现在 | 多人时 |
|---|---|---|
| 追杀 / 伏击（`leaderThreats`） | 只在"玩家"第一时触发 | 只针对**排第一的真人**。真人之间互相打本来就是乐趣，用不着再给第二名的真人加压 |
| 警察（`updatePatrol`） | 跟着玩家 | 跟着排第一的真人；他完赛后换下一个 |
| AI 拉锯（`topNow`） | 围着玩家的位置加速或减速 | 围着**离自己最近的真人** |
| 宿怨（`grudges`） | 存档里的一个 Set | 先不带进多人局；多人局里，打倒过某个真人两次的 AI 会盯上他，只在这一局有效 |

### 1.4 打击停顿和慢动作

- `main.ts` 现在命中时会把模拟停 55–100 ms（hitstop），自己摔车时把模拟放慢到 0.35 倍（slow）。
- **联机时模拟必须跟着服务器的节拍走，不能为某一个人停下来。**
- **推荐：** 两个效果都改成只作用在渲染上：画面冻结 / 放慢，模拟照常往前跑，之后用插值追回来。单机也一起改掉，两边手感一致。
- 暂停按钮在多人局里换成"离开"，要确认两次。

### 1.5 平台

- 第一目标：自己的站（跟 standing 一样，h.gamestao.com 这类）。
- Playgama 的沙盒在 standing 那边挡过排行榜请求（CSP），**要先确认它让不让 WebSocket 连出去**，再决定多人模式要不要进 Playgama 包。
- 如果被挡，Playgama 版就只有单机。

## 2. 确定性护栏（推荐现在就做，1–2 天）

现在的确定性靠的是自觉，代码一改就可能悄悄坏掉。从 standing 搬下面这些过来：

| 件 | 来源 | 作用 |
|---|---|---|
| `determinismLint.test.ts` | standing `engine/` | 扫 `src/sim`，禁止 `Math.sin/cos/sqrt/exp/pow/atan2/hypot/random`、`**`、`Date`、`performance`、`for…in`、`Object.keys/values/entries`，以及从 `src/view` 导入 |
| `hashState` | standing `engine/hash.ts` | 对整个状态求哈希。我们的状态是浮点数，用 `Float64Array` 按位哈希即可 |
| 金哈希测试 + `SIM_VERSION` | standing `Engine.test.ts` | 固定种子加机器人输入跑一整局，哈希写死在测试里；规则改动时有意识地更新它 |
| 回放 | standing `engine/replay.ts` | 回放 = 种子 + 配置 + 每帧输入，以后也用作 bug 报告 |
| vitest | — | moto 现在还没有测试框架，顺手加上 |

**为什么浮点数也可以（standing 用的是整数）：**
- JS 的 number 就是 IEEE-754 双精度，加减乘除每一步都是"正确舍入"。
- 语言规范不允许引擎偷偷做 FMA 融合，也没有 x87 那种 80 位中间精度，所以 V8、SpiderMonkey、JavaScriptCore 算出来逐位相同。
- 会出差异的只有超越函数（`sin` 之类各家实现不同），lint 已经禁了。
- 服务器不跑模拟，也就不存在"服务器用别的语言重写一遍"的问题。
- **要验证一次：** Chrome、Firefox、iOS Safari 各跑同一个金哈希（第 6 节里程碑 1）。

**排序：** `checkFinish` 里的 `.sort((a, b) => b.z - a.z)` 加上 `|| a.id - b.id` 作为最后的平局规则。

## 3. 模拟层改造（多座位）

现在的写法是"一个玩家 + 一群 AI"，`w.player` / `isPlayer` 一共出现在约 25 处（`grep -n "player\|isPlayer" src/sim`）。要改成"N 个真人座位 + AI"：

| 地方 | 现在 | 改成 |
|---|---|---|
| 输入 | 一个 `world.input` | `inputs: Input[]`，按座位编号；`controlPlayer` 对每个真人座位各跑一遍 |
| 输入的格式 | `targetX` 是浮点数，直接从拖动坐标写进去 | **在输入边界量化**：`targetX` 取整到厘米，`steer` 量化成 −127..127，`brake`、`attack` 是位。线上传的是 `{seat, tick, tx, steer, bits}` |
| `standing` | 玩家的名次 | `placeOf(rider)`，每个人都能查 |
| 车流（`updateTraffic`） | 只在玩家前后生成、回收 | 生成窗口覆盖所有真人：最后一名后方到第一名前方。车的数量按真人"团"计；两个真人相距超过 300 m 时，各自周围单独补车 |
| 威胁、警察、AI 拉锯 | 第 1.3 节 | 第 1.3 节 |
| 比赛结束 | 玩家完赛后 1.6 s | 所有真人都完赛或倒下，或者到 `TIME_CAP_S` |
| `botInput` | 写 `w.input` | 写 `inputs[seat]`。headless 时一局里放 2–4 个机器人座位，直接用来测平衡和确定性 |

- 单人局 = 只有一个真人座位。**单机的金哈希不能因为这次改造而变**，这条用来检验重构有没有改错东西。

## 4. 网络模型

### 4.1 服务器：照搬 daydayup

- 要移植的部分：
  - `server/src/MatchRoom.ts`（430 行）、`RoomManager.ts`（101 行）、`windowClock.ts`；
  - `engine/net/FrameBroadcast.ts`（111 行，纯转发逻辑，服务器和测试共用）。
- **节拍器：** 每 100 ms 发一批 3 帧，从不等任何一个玩家。
- **服务器不跑模拟。** 输入按"变化才发"传，到达时间落在哪个 100 ms 窗口，就落在那个窗口对应的帧上。
- **不要的部分：** daydayup 的结算、作弊踢人、门票，以及 funny 的整套控制面（gateway、matchsvc、Redis、JWT）。好友房的房间就放在内存里。
- **部署：** 跟 standing 计划的一样，在已有那台机器上开一个 `/ws`，由 Caddy 代理。

### 4.2 客户端

- `NetInputSource`（daydayup `engine/net/`，268 行）：只按确认过的帧推进；落后时按 3×/5×/10× 追帧。
  - **funny 踩过的坑：** 追帧阶梯在落后 1 秒以内有一段空档，客户端会一直稳定落后约 1 秒。这段要补上。
- 按 30 Hz 匀速播放（daydayup 的 `onlineInterpolation.ts`）。来一批就一口气跑一批的话，远端的人会按 10 Hz 一顿一顿。
- 断线：60 s 宽限期；重连时 `resume{lastTick}` → `resync`，带上整局的帧日志。整局重算不到 0.1 s（手机上估计不到 1 s），**不需要快照**。
- 每 150 帧（5 s）各端上报一次 `hashState`，服务器比对。不一致就结束这局，两边的回放存成问题报告。

### 4.3 本地预测：只预测横向 x（跟 daydayup 的区别）

- **为什么要预测：** 纯帧同步下，你的输入要先到服务器、进帧、再广播回来，大约要一个 RTT（100–200 ms）才生效。
- **daydayup 的做法：** 把自己的角色往前画到"确认位置 + 还在路上的输入"（`LocalPredictor.ts`）。
- **赛车不能整套照搬。**
  - 30 m/s 的车速下，150 ms 的预测领先就是 4.5 m。
  - 如果把自己往前画了 4.5 m，并排挤压、侧面拍打全会错位：明明画面上贴在一起，却打不中。
- **我们的做法：**
  - **z（前进）不预测。** 整个世界都画在同一个确认帧上，彼此之间的相对位置永远是对的。z 本来就由自动油门决定，延迟体感不明显。刹车有约 150 ms 延迟可以接受，以后再看。
  - **x（横向）预测。** 拖动转向是最主要的手感，必须跟手。画出来的 x = 确认帧的 x + 还没被确认的那段转向输入的推演。复用 scene.ts 现有的横向弹簧（`smoothX`），把它的目标从"模拟里的 x"改成"预测的 x"。
  - **预测出来的 x 要被邻居挡住。** 用跟 `contacts()` 一样的 `CONTACT.width` 推开，否则会画出穿过别人的车。
  - **攻击不预测命中。** 按下就立刻播挥手动画和挥空音效（纯表现）；命中由确认帧决定。打击停顿加火花本来就有 55–100 ms，正好盖住这段延迟。
- **完整回滚（GGPO 式）作为第二阶段备选。** daydayup 否掉它，是因为几百个实体在低端手机上重算不起。我们只有 10 个骑手和几十辆车，手机上一帧估计 ~150 µs，每帧回滚 8 帧约 1.2 ms，扛得住。
  - 前提：`World` 要能快照和恢复。现在有私有字段、`Set`，事件也混在状态里，要先整理。
  - **只有当实测发现"拍打不跟手"时才做。**

## 5. 客户端界面

- **大厅面板：**"和朋友比赛" → 显示 6 位房间码和分享链接（`?room=123456`）→ 等人 → 房主点开始。
- **比赛中：**
  - 真人的名牌用不同颜色，带国旗或头像位；
  - 进度条上的真人点画大一号；
  - 远处的真人在屏幕边缘显示箭头和距离。
- 暂停改成离开；hitstop 和慢动作只作用于渲染（第 1.4 节）。
- **结算：** 所有真人的名次和奖金并排显示，每人奖金进自己的存档。
- **提示：**"朋友已离开"、"朋友重连中（60 s）"、"版本不一致，请刷新"（服务器拒绝 `SIM_VERSION` 不同的人加入）、"连接中断"（哈希不一致时）。
- 竖屏和横屏两套布局都要做。
- **埋点：** `mp_room`、`mp_join`、`mp_start`、`mp_end{place, humans, reason}`、`mp_desync`。

**里程碑：**
1. **同一台机器开两个标签页：** 第 1–3 步加一个最简客户端，连本地服务器。顺便在 Chrome、Firefox、iOS Safari 上各跑一次金哈希，确认浮点数一致。约 1.5 周。
2. **跨公网：** 加上预测、追帧、重连。拿手机 4G 对桌面，重点看并排拍打跟不跟手。如果不跟手，再评估第 4.3 节的完整回滚。
3. **能上线：** 界面、文案、平衡。先上自己的站；Playgama 等 WebSocket 确认过后再说。

## 7. 什么时候做

- **第 1 步（护栏）现在就做。** 只要 1–2 天，能防止以后的单机改动悄悄破坏确定性；回放顺手还能当 bug 报告用。
- **第 2–6 步等单机版有了数据再做。** 先看留存和局数：如果单人模式都留不住人，多人也救不了。参考 standing 的判断：上线后看有多少局是从分享链接开始的。
- **提前铺路：** 只要第 2 节的规则一直守着，单机的新功能（新武器、新威胁）以后都能直接进多人模式，不用返工。
